## Goal

Replace the hand-written builders of the two launch types with builders generated by the
[`bon`](https://bon-rs.com) crate, so that a setting is declared once (on the field) instead of
three times (field, builder field, setter), and the setters, their `maybe_` forms and their docs
come from the declaration:

* `BrowserConfig` (`src/browser/config.rs:176-277`), configured today with 80 `with_*` methods;
* `LaunchOptions` (`src/sb_cdp/launch.rs:183-238`), built today by the hand-written
  `LaunchOptionsBuilder` (`src/sb_cdp/launch.rs:473-516`), which copies 36 fields, has its own
  `Default` (`:518-562`) and moves every field across in `assemble` (`:1053-1120`).

Breaking changes are fine (no users yet, no shims). Names follow this project's patterns: plain
setter names on builders, `with_*` on an owned value that is not a builder, one name per thing.

## The answer in short

* **`BrowserConfig` should keep its `with_*` methods.** It is not built once: it is loaded
  (`Settings::to_browser_config`, 63 lines; `BrowserConfig::from_env`, 16; serde) and then
  changed. A bon builder starts empty and cannot start from a loaded value, and 58 of the 80
  setters are not plain setters of a `BrowserConfig` field (see "BrowserConfig: keep the
  `with_*` methods" below).
* **`LaunchOptions` can take a bon builder**, with the design in
  [LaunchOptions with bon](#launchoptions-with-bon): 23 setters generated, 19 kept by hand (18
  on builder fields, `fingerprint` over a hidden generated setter), one custom `build`. It needs one rule change (an explicit setting always wins
  over the `BrowserConfig` and the fingerprint, whatever the order of the calls), and it changes
  how consumers that store or pass a half-built builder work (stealth: 18 sites).
* **Whether to take bon for it is the first open question.** `LaunchOptions` has no required
  member, so the typestate brings only the set-at-most-once check, which our layering of
  settings works against. A hand-written builder over one struct removes the same duplication
  without the dependency or the consumer churn. My recommendation is in
  [Open questions](#open-questions).

## What bon generates (read on Context7)

* `#[derive(bon::Builder)]` on a struct gives `Type::builder()`, a setter per member and
  `build()`. `#[bon::bon]` on an `impl` with `#[builder]` on `fn new` gives the same names for a
  constructor function (guide, overview).
* A member of type `Option<T>` is optional: the setter takes `T`, and a `maybe_` setter takes
  `Option<T>`. `#[builder(default)]` and `#[builder(default = expr)]` make any other type
  optional, with the same pair of setters (guide, optional members).
* `#[builder(into)]` on a member, or `#[builder(on(String, into))]` on the struct, makes a setter
  take `impl Into<T>` (guide, into conversions).
* `#[builder(with = closure)]` changes what a setter takes: several parameters (the `maybe_`
  setter then takes an `Option` of a tuple), `impl Trait` in a parameter, and a closure that
  returns a `Result`, which makes the setter return a `Result` (reference, `with`).
* `#[builder(field)]` puts a private field on the builder with no setter, initialised with
  `Default::default()`; hand-written methods on `impl<S: State> TypeBuilder<S>` can change it and
  return `Self`, any number of times, and `build` moves it into the struct (reference, `field`;
  guide, builder fields).
* `#[builder(setters(vis = "", name = other))]` hides a generated setter so that a hand-written
  one with the public name can wrap it, with an `S::Member: IsUnset` bound and the
  `SetMember<S>` return type (guide, custom methods).
* `#[builder(finish_fn(vis = "", name = build_internal))]` hides the generated finish function,
  so a hand-written `build` on `impl<S: IsComplete> TypeBuilder<S>` can check the value and return
  a `Result` (guide, fallible builders).
* `#[builder(derive(Clone, Debug))]` derives them for the builder. Its `Debug` prints only the
  members that were set, and the format "is not stable and may change between patch versions"
  (reference, `derive`).
* `#[builder(getter)]` adds `get_member()`, "only callable after the corresponding member has
  been set"; an optional member's getter returns `Option<&T>` (reference, `getter`).
* `#[builder(skip)]` leaves a field out of the builder; `#[cfg]` on a field works with the derive,
  because the compiler expands it first (bon 2.2 release notes).
* **The typestate.** "The builder's type changes with every setter call": `ExampleBuilder`,
  then `ExampleBuilder<SetX1>`, then `ExampleBuilder<SetX2<SetX1>>`; the state `Empty` is the
  default (guide, the builder's type signature). Setting a member twice does not compile, unless
  `#[builder(overwritable)]`, which is "experimental", behind the cargo feature
  `experimental-overwritable`, with "breaking changes between minor releases" (reference,
  `overwritable`). A builder that differs by branch is written as a shared partial builder with
  `build()` called in each branch (guide, conditional building).

None of the pages read starts a builder from an existing value: a builder starts at `builder()`
(or a start function) and holds only what was set on it since.

## What the typestate meets in our call sites

| Call shape | Today | With a bon builder | Where |
|---|---|---|---|
| One chain, then `build()` | works | works, same text | most of the 286 `LaunchOptions::builder()` lines |
| A member set twice | the last wins | does not compile | the fingerprint before or after an explicit setting (`src/mcp/cdp/session.rs:104-111` relies on the order); a setter after `browser_config` (`tests/offline/sb_cdp_mobile.rs:345-348`, were `no_sandbox` a member) |
| A member set inside an `if` on a reassigned `let mut builder` | works | does not compile (the type changes) | 10 in core, 2 in stealth, 1 in the companion ([counts](#call-site-counts)) |
| A function, closure or struct field typed `LaunchOptionsBuilder` | works | accepts only the empty state | 10 helpers in core; stealth: 4 fields, 2 `launch_options` setters, `configure_launch`, 4 test helpers |
| A setter that sets other members | works | impossible from a method that returns `Self` | `fingerprint`, `mobile`, `device_metrics`, `virtual_display`, `switch`, `browser_config` |
| Reading what was set | builds a clone (`crates/wire/src/mitm/mod.rs:813-817` in stealth: "the builder has no getter") | a getter exists only once the state says "set" | the stealth start page, and its fingerprint (Decision 2, below) |

A setter that bon generates for a member changes the builder's type; a hand-written method on a
`#[builder(field)]` returns `Self`. So everything that is added to, toggled or layered has to be a
builder field, and everything a method sets for another has to move into `build`.

## Proposal

### BrowserConfig: keep the `with_*` methods

* It is a value, not a builder: 63 lines start from `Settings::to_browser_config()` and 16 from
  `BrowserConfig::from_env()`, and serde reads it from files. The golden template
  `tests/golden/cli/mkfile/cm_uc.rs.golden:15-17` is the usual shape:
  `Settings::load()?.to_browser_config().with_mode(DriverMode::Uc)`. A bon builder starts empty,
  so it could only add a second way to make one (`BrowserConfig::builder()...build()`), next to
  `default()` and `from_env()`, and the 486 `BrowserConfig::default()` lines and every
  `to_browser_config().with_*` chain would keep the hand-written methods anyway.
* Only the 22 "set one field" setters are what bon generates. The other 58 set a field of
  `launch` or a switch, set two fields, convert their argument, add to a list, return a `Result`,
  or are another name for a setter.
* `#[builder(default)]` would use each field's `Default`, which is not `BrowserConfig::default()`
  (`RuntimeConfig` sets headless and `auto_start_driver` on, `:356-384`) unless every field gets
  its own `default = ...`.
* The project's own naming note already calls `BrowserConfig::with_proxy` "a consuming setter on
  an owned value that is not a builder" (stealth `docs/design/stealth_names.md:233-236`).

What can shrink without bon: the 26 one-line switch setters (`:733-1019`) could come from a
private `macro_rules!` table (name, `LaunchSwitch`, doc line). That is a separate change and is
open question 3.

### LaunchOptions with bon

The derive goes on `LaunchOptions` itself, which then holds what the caller set, plus one
crate-private `resolved` field that `build` fills. `LaunchOptionsBuilder` keeps its name (bon's
default for `LaunchOptions` is `LaunchOptionsBuilder`), so `LaunchOptions::builder()` and
`.build()?` stay as they are.

```rust
#[derive(Debug, Clone, bon::Builder)]
#[builder(
    derive(Clone, Debug),
    on(String, into),
    finish_fn(vis = "", name = build_internal),
)]
#[expect(clippy::struct_excessive_bools, reason = "independent on/off switches")]
pub struct LaunchOptions {
    // Members: each set at most once, with a setter and a `maybe_` setter.
    pub(crate) url: Option<String>,
    #[builder(with = |url: impl Into<String>| Redacted(url.into()))]
    pub(crate) cdp_url: Option<Redacted>,
    pub(crate) cdp_target: Option<String>,
    pub(crate) headless: Option<bool>,
    #[builder(default)]
    pub(crate) use_chromium: bool,
    #[builder(into)]
    pub(crate) executable_path: Option<PathBuf>,
    #[builder(default)]
    pub(crate) ad_block: bool,
    #[builder(with = |proxy: impl Into<String>| Redacted(proxy.into()))]
    pub(crate) proxy: Option<Redacted>,
    #[builder(into)]
    pub(crate) user_data_dir: Option<PathBuf>,
    pub(crate) user_agent: Option<String>,
    pub(crate) lang: Option<String>,
    #[builder(with = |width: u32, height: u32| (width, height))]
    pub(crate) window_size: Option<(u32, u32)>,
    #[builder(with = |x: i32, y: i32| (x, y))]
    pub(crate) window_position: Option<(i32, i32)>,
    pub(crate) webrtc_policy: Option<WebRtcPolicy>,
    #[builder(default)]
    pub(crate) shield_webrtc: bool,
    // The public `fingerprint(&Fingerprint)` is hand-written over this one.
    #[builder(setters(vis = "", name = fingerprint_owned))]
    pub(crate) fingerprint: Option<Fingerprint>,
    pub(crate) mobile: Option<bool>,
    pub(crate) device_metrics: Option<DeviceMetrics>,
    #[builder(default)]
    pub(crate) proxy_bypass_list: ProxyBypassList,
    #[builder(with = |url: impl Into<String>| Redacted(url.into()))]
    pub(crate) proxy_pac_url: Option<Redacted>,
    pub(crate) virtual_display: Option<VirtualDisplay>,
    #[builder(default = DEFAULT_STARTUP_TIMEOUT)]
    pub(crate) startup_timeout: Duration,
    #[builder(default)]
    pub(crate) debugging_port: u16,
    #[cfg(feature = "plugins")]
    #[builder(default)]
    pub(crate) plugins: seleniumbase_rs_plugin::PluginSet,

    // Builder fields: no generated setter; hand-written methods returning
    // `Self` add to them, any number of times, in any order.
    #[builder(field)]
    pub(crate) extra_args: Vec<String>,
    #[builder(field)]
    pub(crate) extensions: Vec<PathBuf>,
    #[builder(field)]
    pub(crate) prefs: Map<String, Value>,
    #[builder(field)]
    pub(crate) switches: BTreeSet<LaunchSwitch>, // incognito and guest included
    #[builder(field)]
    pub(crate) no_sandbox: Option<bool>, // unset: `SB_NO_SANDBOX` decides
    #[builder(field)]
    pub(crate) disable_features: Vec<String>,
    #[builder(field)]
    pub(crate) enable_features: Vec<String>,
    #[builder(field)]
    pub(crate) host_resolver_rules: Vec<String>,
    #[cfg(feature = "plugins")]
    #[builder(field)]
    pub(crate) selection: crate::config::plugins::PluginSelection,
    #[builder(field)]
    pub(crate) browser_config: Option<Box<BrowserConfig>>,

    // Only plugins set this, on the built options (as today, `launch.rs:218-219`).
    #[builder(skip)]
    pub(crate) disable_quic: bool,
    // Worked out by `build` from everything above: the parsed proxy and PAC
    // URL, the `StealthPlan`, the phone, the browser source, the profile mode,
    // the merged preferences and features.
    #[builder(skip)]
    pub(crate) resolved: Resolved,
}

impl<S: launch_options_builder::IsComplete> LaunchOptionsBuilder<S> {
    /// Checks the combination and works out what the browser is started with.
    pub fn build(self) -> Result<LaunchOptions, SeleniumBaseError> {
        let mut options = self.build_internal();
        options.resolve()?;
        Ok(options)
    }
}
```

`resolve` is today's `build` plus `assemble`, with one precedence rule instead of call order:

> A value set on the builder wins; else the value of the `BrowserConfig` given to
> `browser_config`; else the fingerprint's (the builder's, else the config's); else the default.

Today `browser_config` overwrites what was set before it and is overwritten by what comes after
it, and the fingerprint fills only what is unset when it is called. Under the rule the order of
the calls no longer matters, which is the only meaning "set at most once" can have here. The
phone: an explicit `mobile(false)` turns it off whatever else asks for one; `mobile(true)` or a
`device_metrics` turns it on. `headless` unset means headed when a `virtual_display` is given, and
otherwise headless on Linux only, as `is_headless` does today (`:269-271`).

### What stays hand-written, and why

| Item | Why bon does not generate it |
|---|---|
| `fingerprint(&Fingerprint)`, and a new `maybe_fingerprint(Option<&Fingerprint>)` beside it | takes a reference; the bon pages read show `with` closures with values and `impl Trait`, not a reference, so both wrap the hidden `fingerprint_owned` with the documented custom-setter pattern (`S::Fingerprint: IsUnset`) |
| `arg`, `extension`, `preference`, `disable_features`, `enable_features`, `host_resolver_rules`, `plugins_named`, `plugin_selection` | they add to a builder field, any number of times |
| `switch`, `dark_mode`, `devtools`, `disable_web_security`, `swiftshader`, `maximize`, `incognito`, `guest`, `no_sandbox` | they toggle one entry of the `switches` field (`no_sandbox` its own tri-state field); `incognito` and `guest` move into `switches` (one place per setting, `LaunchSwitch` already names them), and the incognito-with-guest check stays in `build` |
| `browser_config(&BrowserConfig)` | it would set about 20 members; it stores the config in a builder field instead, and `resolve` reads it under the precedence rule |
| `build` | it can fail, and it resolves (fallible-builders pattern) |
| `Default for LaunchOptions` | it must not fail and today skips the checks (`:240-244`); it becomes `builder().build_internal()` plus the default resolution |
| `LaunchOptions::fingerprint()` and `LaunchOptions::with_fingerprint(self, &Fingerprint)` (new) | for stealth, which holds built options (below); `with_*` because `LaunchOptions` is an owned value |

Of the 42 setters, 23 are generated (each with a `maybe_` form) and 19 stay hand-written
(`maybe_fingerprint` is new); `build` and `Default` stay. From the line ranges above, about 240 lines of hand-written code go (the
builder struct, its `Default`, the plain setters, the field moves of `assemble`) and about 60
lines of attributes come.

## Consequences

* **Compile time.** bon's own benchmark builds 10 structs of 50 fields in 2.096 s against 0.112 s
  without macros (guide, compilation benchmarks); one struct of about 40 members is a fraction of
  that. `bon-macros` builds on darling 0.24 and syn 3 (bon's `Cargo.toml`), and both are already
  in our tree (`Cargo.lock:1369-1370` darling 0.24.1, `:6620-6621` syn 3.0.9), so the new crates
  are `bon` and `bon-macros`. Measure with `cargo build --timings` in step 3.
* **Error messages.** Setting a member twice is a trait-bound error on the member's state
  (`IsUnset`) instead of a silent overwrite. The exact text is to verify in step 3 and belongs in
  the reference page.
* **Rustdoc.** `LaunchOptionsBuilder` becomes generic over its state, each generated setter
  returns `LaunchOptionsBuilder<SetMember<S>>` and asks that the member is still unset, and a
  generated module
  `launch_options_builder` holds the state types that helpers name. To verify on the rendered
  page in step 3: that the field docs reach the setters, and the module's visibility.
* **Debug.** The builder's derived `Debug` prints only the members that were set, in a format bon
  does not keep stable; `tests/offline/sb_cdp_mobile.rs:463-464` asserts on it and moves to the
  built options. `Redacted` keeps the passwords out. To verify: that a crate-private `Redacted` as
  the type of a member of a public builder compiles without a private-in-public error; if not,
  `Redacted` becomes public with a private field.
* **Lints.** `src/sb_cdp/` is held to the pedantic lint set: the generated code must pass
  `cargo clippy --all-targets --features "mcp-server test-util testing bdd" -- -D warnings`.
* **MSRV.** bon's `Cargo.toml` on master says `rust-version = "1.88.0"`; ours is 1.99. Pin the
  version `cargo add bon` picks and check its `rust-version`.
* **serde and Default.** `LaunchOptions` has no serde. Its `Default` stays hand-written (above).
  `BrowserConfig`, which keeps its methods, keeps its serde attributes and its `RuntimeConfig`
  default untouched.
* **Not affected.** The `dev` server's API index (`src/mcp/dev/api/index_gen.rs:3-7`) covers
  `BaseCase`, `Browser`, `Page`, `Locator` and `BrowserContext`, not the builders. The notes in
  `parity/api.toml` name setters that keep their names. `Settings::to_launch_options`
  (`src/config/launch_map.rs:261-339`) keeps its signature, so the golden templates do not move.

## The stealth follow-up and `get_shadow_root`

**(a) Stealth's builders and the fingerprint.** Decision 2 of the stealth naming note
(`docs/design/stealth_names.md:212-214` there) has the stealth builders read the first fingerprint
from the `LaunchOptionsBuilder` given to `launch_options`, and drop their own setter. Today the
builder cannot be read (it stores only the `StealthPlan`, `launch.rs:493`, `:649`). A bon getter
does not help: it is callable only once the state says the member was set, and a builder handed
to `launch_options` has a state the stealth code does not know. Hence step 1
(`LaunchOptions::fingerprint()`) and stealth holding built options. Without bon, step 1 plus a
plain getter on the builder would do.

**(b) `get_shadow_root`.** It still returns a thirtyfour type: `BaseCase::get_shadow_root`
(`src/api/base_case.rs:2083-2095`) returns `crate::drivers::WebElement`, the re-export of
`thirtyfour::WebElement` (`src/drivers.rs:45-47`). It is not alone: 13 signatures in `src/api/`
return that type (`src/api/base_case.rs:2087`, `:2293`, `:3576`, `:3584`;
`src/api/base_case_impls/base_case_impl_extra.rs:544`, `:559`, `:573`, `:585`, `:1629`, `:1660`,
`:1682`; `base_case_impl_highlight.rs:152`; `base_case_impl_shadow.rs:27`). A shadow-root type of
our own for one of them would leave the element the next call returns foreign. It is open
question 6.

## Open questions

1. **bon for `LaunchOptions`, or one hand-written struct?** The alternative keeps a hand-written
   `LaunchOptionsBuilder` that wraps a `LaunchOptions` (setters write into it, `build` checks and
   resolves): the 36-field copy, the second `Default` and the field moves go the same way, every
   consumer pattern (stored, passed, reassigned, read) keeps working, and no dependency comes.
   It loses the `maybe_` setters and the setter docs taken from the fields, and the set-once
   check, which here only gets in the way, because `LaunchOptions` has no required member.
   **Recommendation:** do steps 1 and 2 (useful either way), then take the one-struct builder
   rather than step 3; take bon only if the owner wants the `maybe_` setters and generated docs
   more than the stealth changes cost (18 sites there, 20 in core).
2. **The precedence rule (explicit, then the config, then the fingerprint, then the default).**
   **Recommendation:** yes. It replaces two order rules that the docs have to explain
   (`docs/api/cdp-browser.md:138`, `:141`) and that `src/mcp/cdp/session.rs:104` has to comment.
3. **The 26 switch setters of `BrowserConfig`.** **Recommendation:** keep `BrowserConfig` off bon;
   if the repetition matters, a private `macro_rules!` table in its own small commit, so each
   setter keeps its doc line and its Python flag names.
4. **How stealth layers on core's launch settings.** Built `LaunchOptions` with owned-value
   setters (`with_fingerprint`, and what `configure_launch` needs: the proxy, extra arguments, a
   start page), or stealth code generic over `launch_options_builder::State`. **Recommendation:**
   built options; generic signatures would put bon's state module into stealth's public API.
5. **`#[builder(overwritable)]` to keep "the last call wins".** **Recommendation:** no. It is
   experimental (`experimental-overwritable`, breaking changes between minor releases) and the
   builder's type would still change with every setter, so stored builders stay broken.
6. **`get_shadow_root` and the other 12 signatures returning `thirtyfour::WebElement`.**
   **Recommendation:** not in this lane. One lane gives the WebDriver engine an element type of
   its own for all 13, so one name means one element type across `BaseCase`.
7. **The other hand-written builders** (`PoolOptionsBuilder`, `src/sb_cdp/pool.rs:100`;
   `BehaviorBuilder`, `src/evasion/behavior.rs:149`; `FingerprintBuilder`,
   `src/evasion/fingerprint.rs:1530`). **Recommendation:** none now. `FingerprintBuilder` is the
   clearest misfit: it starts from an existing value (`Fingerprint::to_builder`,
   `fingerprint.rs:780`) and is passed through 11 helpers (`src/profile_payloads/profile.rs:805-1173`).
   `PoolOptionsBuilder` could follow if `LaunchOptions` goes to bon.
